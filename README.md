# IncidentForge

### Multi-Agent AI System for Production Incident Investigation

IncidentForge is a multi-agent engineering incident response system that investigates production incidents through a virtual team of specialized AI engineers.

Rather than relying on a single agent to diagnose an incident, IncidentForge decomposes the investigation across specialized engineering roles. Agents independently collect evidence from logs, metrics, traces, repositories, deployments, and databases before contributing their findings to an Incident Commander.

The Incident Commander correlates evidence, evaluates competing hypotheses, resolves conflicting findings, and produces a root-cause assessment and remediation recommendation.

Built with **Python, Google ADK, Gemini, FastAPI, React, and TypeScript.**

---

## Overview

Production incidents rarely have a single obvious explanation.

A sudden increase in API latency could be caused by:

* a recent deployment
* database contention
* a downstream dependency
* infrastructure degradation
* configuration changes
* unusual traffic
* resource exhaustion

Traditional monitoring systems can identify that something is wrong. IncidentForge focuses on determining **why it is happening** and **what should be done next**.

The system models incident response as a collaborative engineering workflow:

```mermaid
flowchart TD
    A["Production Incident"] --> B["Incident Commander"]

    B --> C["Investigation Planning"]

    C --> D["Observability Agent"]
    C --> E["Repository Agent"]
    C --> F["Database Agent"]

    D --> G["Evidence Store"]
    E --> G
    F --> G

    G --> H["Hypothesis Analysis"]
    H --> I["Evidence Validation"]
    I --> J["Root Cause Assessment"]

    J --> K["Recommendation Engine"]
    K --> L["Remediation Recommendation"]
```

## Agent Team

IncidentForge models incident response as a team of specialized engineering roles. Each agent has a defined responsibility, toolset, and investigation perspective.

### Incident Commander

The Incident Commander is the coordinating agent responsible for managing the overall investigation.

Responsibilities include:

* understanding the incident and establishing severity
* decomposing the investigation into specialized tasks
* delegating tasks to appropriate agents
* maintaining shared incident state
* correlating findings from multiple agents
* identifying contradictory evidence
* ranking competing root-cause hypotheses
* determining when sufficient evidence has been collected
* coordinating remediation planning

The Incident Commander does not simply select the answer generated by another agent. It synthesizes evidence collected across the investigation.

---

### Observability Agent

Investigates the system through operational telemetry.

Analyzes:

* application logs
* service metrics
* distributed traces
* latency distributions
* error rates
* resource utilization
* service health

Its primary responsibility is determining **where abnormal behavior originates and how it propagates through the system**.

---

### Repository Agent

Investigates application-level behavior and recent software changes.

Analyzes:

* recent deployments
* Git commits
* code changes
* API behavior
* dependency changes
* application architecture

The Repository Agent can correlate an incident with a recently introduced application change.

---

### Database Agent

Investigates failures originating from the data layer.

Analyzes:

* query latency
* slow queries
* database resource utilization
* connection pools
* locks
* transaction behavior

An important responsibility is also **eliminating the database as a root-cause candidate when available evidence does not support that hypothesis**.

## Agent Collaboration

The agents are not intended to behave as a simple sequence of prompts.

Each specialist investigates the incident independently and contributes structured findings to the shared investigation state.

```mermaid
sequenceDiagram

    participant IC as Incident Commander
    participant O as Observability Agent
    participant R as Repository Agent
    participant D as Database Agent
    participant E as Evidence Store

    IC->>O: Investigate telemetry anomalies
    IC->>R: Investigate recent application changes
    IC->>D: Investigate database health

    O->>E: Submit telemetry findings
    R->>E: Submit code/deployment findings
    D->>E: Submit database findings

    E-->>IC: Return consolidated evidence

    IC->>IC: Rank hypotheses
    IC->>IC: Resolve conflicting findings
    IC->>IC: Determine root cause confidence
```

This allows the system to reason from **multiple independent perspectives** rather than relying on a single model response.

## Evidence-Driven Reasoning

A core design principle of IncidentForge is:

> **Agent conclusions are hypotheses; evidence is what determines confidence.**

Each agent contributes structured findings.

For example:

```text
Agent: Database Engineer

Finding:
Database query latency remained within normal limits.

Evidence:
Average query latency: 22 ms
Database CPU: 34%
Lock contention: None

Hypothesis:
Database degradation

Confidence:
Low
```

Another agent may report:

```text
Agent: Repository Engineer

Finding:
A synchronous inventory service call was introduced
during the latest checkout deployment.

Evidence:
Deployment: checkout-service v1.8.2
Commit: 8f31a2

Hypothesis:
Downstream inventory dependency causing request blocking

Confidence:
High
```

The Incident Commander uses these findings to update the relative confidence of competing hypotheses.

```mermaid
flowchart LR

    A["Agent Findings"] --> B["Evidence Normalization"]
    B --> C["Hypothesis Generation"]

    C --> D["Evidence Validation"]

    D --> E["Supporting Evidence"]
    D --> F["Contradicting Evidence"]

    E --> G["Hypothesis Scoring"]
    F --> G

    G --> H["Ranked Hypotheses"]
    H --> I["Incident Commander"]
```

## Investigation Lifecycle

IncidentForge uses a canonical investigation state machine:

```mermaid
stateDiagram-v2

    [*] --> Queued

    Queued --> Running

    Running --> Analyzing

    Analyzing --> Synthesizing

    Synthesizing --> Completed

    Running --> Failed
    Analyzing --> Failed
    Synthesizing --> Failed

    Completed --> [*]
    Failed --> [*]
```

**Canonical Status States:**
- `queued` — Investigation created, waiting to start
- `running` — Investigation actively executing (triage phase)
- `analyzing` — Specialist agents collecting evidence (observability, repository, database)
- `synthesizing` — Incident Commander correlating findings, generating hypotheses
- `completed` — Investigation finished with recommendations
- `failed` — Unrecoverable error occurred

**Progress milestones** are tied to actual execution stages:
- queued: 0%
- triage: 10%
- observability: 25%
- repository: 45%
- database: 65%
- correlation: 75%
- synthesis: 85%
- recommendation: 95%
- completed: 100%

## Google ADK Integration

IncidentForge uses **Google Agent Development Kit (ADK)** as its agent orchestration framework.

The system is structured around:
* specialized agents with ADK `Agent` instances
* agent delegation via the Incident Commander
* tool-based execution using ADK `FunctionTool` wrappers
* shared investigation state passed between agents
* structured outputs using Pydantic models as `output_schema`
* modular workflows with deterministic fallback when API keys are unavailable

For example:

```mermaid
flowchart TD

    IC["Incident Commander (ADK Agent)"]

    IC --> O["Observability Agent (ADK Agent)"]
    IC --> R["Repository Agent (ADK Agent)"]
    IC --> D["Database Agent (ADK Agent)"]
```

Each specialist agent:
1. Is instantiated as a Google ADK `Agent` with a model, instruction, and tools
2. Has deterministic tools exposed as ADK `FunctionTool` for logs, metrics, traces, git, deployments, and database analysis
3. Uses the ADK `Runner` and `InMemorySessionService` for execution
4. Returns structured `Finding` objects via `output_schema`
5. Falls back to deterministic analysis when Google API key is not configured

## API & Real-time Updates

**REST API (FastAPI):**
- `POST /api/v1/investigations` — Create investigation from scenario or manual input
- `GET /api/v1/investigations` — List all investigations
- `GET /api/v1/investigations/{id}` — Get investigation summary
- `GET /api/v1/investigations/{id}/state` — Get full investigation state
- `GET /api/v1/investigations/{id}/timeline` — Get timeline events
- `GET /api/v1/investigations/{id}/evidence` — Get collected evidence
- `GET /api/v1/investigations/{id}/findings` — Get agent findings
- `GET /api/v1/investigations/{id}/recommendations` — Get recommendations
- `POST /api/v1/investigations/{id}/recommendations/{index}/approve` — Approve recommendation
- `POST /api/v1/investigations/{id}/recommendations/{index}/reject` — Reject recommendation

**Server-Sent Events (SSE):**
- `GET /api/v1/investigations/{id}/stream` — Live investigation updates
- Emits: initial state snapshot, timeline events, completion signal
- Handles reconnection with event cursor to prevent duplicate replay

## Evaluation

Agentic systems should be evaluated using repeatable scenarios rather than only qualitative demonstrations.

IncidentForge includes a test suite that validates:

- Investigation completes successfully for each scenario
- Expected evidence types are discovered (metric, log, trace, code, deployment, database)
- Findings are produced by each invoked agent
- Hypotheses are synthesized from findings
- Recommendations are generated with approval requirement
- Timeline contains all key investigation events
- State transitions follow canonical state machine

Run evaluation:
```bash
pytest tests/ -v
```

## Safety and Human Oversight

IncidentForge follows a **recommendation-first** approach.

The system can investigate incidents and evaluate potential recovery strategies, but destructive production actions are not executed without explicit authorization.

```mermaid
flowchart LR

    A["Incident"] --> B["Investigation"]
    B --> C["Root Cause Assessment"]
    C --> D["Remediation Recommendation"]
    D --> E["Human Approval"]
    E --> F["Execution"]
```

Recommendations are created with `requires_approval: true` by default. The API provides approve/reject endpoints that update recommendation status and emit timeline events.

## Quick Start

### Prerequisites
- Python 3.11+
- Node.js 18+
- (Optional) Google API key for LLM-enhanced analysis

### Backend
```bash
cd /path/to/IncidentForge
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Optional: Set Google API key for LLM mode
export GOOGLE_API_KEY=your-key-here

# Start backend
uvicorn app.main:app --reload --port 8000
```

### Frontend
```bash
cd frontend
npm install
npm run dev
```

### Run Demo
1. Open http://localhost:5173 (frontend)
2. Click "New Investigation"
3. Select "payment_latency" or "db_lock_contention"
4. Click "Start Investigation"
5. Watch live updates via SSE on the Investigation Detail page

## Design Principles

### Specialization over Generalization

Each agent is responsible for a clearly defined engineering domain.

### Evidence over Opinions

Agent conclusions are treated as hypotheses and must be supported by evidence.

### Collaboration over Sequential Prompting

Agents contribute independent perspectives and can challenge competing hypotheses.

### Recommendation before Automation

The system separates investigation and recommendation from production execution.

### Continuous Evaluation

Agent behavior is measured using repeatable incident scenarios.

### Extensibility

New agents, tools, data sources, and incident scenarios can be introduced without changing the core architecture.
